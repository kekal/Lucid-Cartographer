- **SetNull / Cascade delete-behavior tests** — `Data/AppDbContext.cs`. The Start/Finish FKs use `OnDelete(SetNull)` and the RouteSegment endpoint FKs use `OnDelete(Cascade)`, but no test deletes a `Poi` to verify the references null / the cached legs evict. Not required by Story 1.1's ACs — add when the Trip ordering/cache services (Story 1.2+/Epic 2) exercise deletes.

## Deferred from: code review of 1-3-render-ordered-stops-connecting-legs-and-the-stop-panel (2026-06-12)

- **Closing leg vs designated Start** — `LucidCartographer/Components/Shared/Trip/TripViewModel.cs` `BuildLegs`. The Roundtrip closing leg is hard-coded back to `stops[0]` (Order 1) and the "finish == start" check compares `finishPoiId == stops[0].PoiId` rather than `== startPoiId`. Phase-1 Start is always Order 1 so this is correct today, but it will draw the closing leg to the wrong stop once Story 1.7 lets the user designate a Start that is not Order 1. Mitigated by Blazor Server's single-threaded circuit; harden if trip state ever updates off the renderer thread.

## Deferred from: code review of stories 1-5/1-6/1-7 (2026-06-14)

- **Pin/order ops are not atomic under true concurrency** — `LucidCartographer/Services/Trip/TripOrderingService.cs` (`SetPinAsync`/`ReorderStopAsync`/`ReconcileOrderAsync`). Each operation reads pins/rows in one `AsNoTracking` context, validates, then writes via separate `WritePinsAsync` + `SetOrderAsync` contexts; only `SaveChangesAsync` is under `SqliteWriteLock.Gate`, so the read-validate-write of the pin pair is not a single transaction. A concurrent editor of the same collection could slip between the validate and the write. Low risk today: single-user self-hosted app, Blazor circuit serializes per-user calls, and the `PoiCollection.Version` token catches a concurrent collection edit on the pin write. Revisit if multi-writer ordering (TSP-Sort 3.1 / MCP 3.2) runs off the renderer thread — same root concern as the 1-2 "OrderIndex write-path atomicity" defer.
- **Trip View stays enabled below the ≥2 placeable gate** — `LucidCartographer/Components/Shared/Trip/TripViewModel.cs` `RefreshAfterMembershipChangeAsync`. Dropping to <2 placeable stops (removal, or a stop going Unplaceable) flips `IsToggleAvailable` false so the toggle disappears, yet `IsTripViewEnabled` stays true — overlays remain with no control to disable them, and at exactly 1 placeable stop the Set-as-Start/Finish controls stay live on a legless trip. Duplicate of the 1-3 "Stuck-on Trip View below the ≥2 gate" defer; resolve together by auto-disabling (and persisting off) or keeping the toggle visible-but-disabled when placeable count drops below 2.
