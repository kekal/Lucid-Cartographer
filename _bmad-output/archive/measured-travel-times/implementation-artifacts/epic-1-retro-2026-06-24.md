# Epic 1 Retrospective — Smarter honest default (smart-haversine)

**Date:** 2026-06-24 · **Mode:** YOLO (autonomous, no tmux — Windows manual cycle)
**Feature:** Travel-time provider upgrade — smart-haversine estimate (per-mode detour factor)

## Outcome

Epic 1 (3 stories) complete. The zero-infrastructure default provider now applies a
per-mode detour/winding factor to the great-circle distance before deriving duration —
materially more realistic estimates, still badged honestly as **Estimated**, still no infra.

- **1.1** Configurable per-mode detour factors — `DriveDetourFactor`/`CycleDetourFactor`/
  `WalkDetourFactor` (shipped `[ASSUMPTION]` defaults 1.3/1.2/1.15) + `DetourFactorFor(mode)`
  accessor mirroring `SpeedFor`; Any/Air → 1.0. Bindable from the existing `TravelTime`
  config section (FR-2).
- **1.2** Apply the factor in the single estimate path — `EstimatedTravelTime.Compute` now
  computes `adjustedMeters = haversine × DetourFactorFor(mode)` then
  `seconds = round(adjustedMeters ÷ SpeedFor(mode))`. Because it is the sole estimate edge,
  the Mock default AND the provider-failure fallback both report the adjusted value with no
  second site (FR-1, FR-3, FR-4 / TRIP-DEGRADE-01). Any/Air stays Placeholder (factor 1.0).
- **1.3** Keep trip ordering mode-invariant (TSP guard) — confirmed + pinned that the TSP cost
  matrix (`DistanceMatrixService`) stays on RAW haversine and never the detour-adjusted
  distance (AD-1 / RD3). Added a source guard comment + a regression test asserting the
  computed Stop Order is byte-identical under default vs. exaggerated detour configs.

**FRs delivered:** FR-1, FR-2, FR-3, FR-4 (Epic 1's estimate-rung FRs); FR-17's Estimated rung
preserved (no new badge type).

## Lessons / Action Items

- **A1 — One estimate edge pays off again.** Because `EstimatedTravelTime.Compute` is the single
  DRY estimate edge (established in the earlier trip-planning epic), FR-1 and the FR-4 degrade
  path were satisfied by a *one-line* change with zero risk of the default and fallback drifting.
  *Standing value:* keep the single-edge invariant; it is why this epic was a 3-file change.
- **A2 — The detour factor must never reach the TSP matrix (AD-1).** The guard already held in
  code (`DistanceMatrixService` ignores `TravelTimeOptions`), but Story 1.3 made it *enforced*
  via a regression test that varies detour factors and asserts identical order, plus a source
  comment. *Standing rule:* accuracy improvements to the estimate path must never silently
  change route order — pin it with a test, not a comment alone.
- **A3 — Test re-alignment vs test-weakening.** Two existing tests asserted equal ground-mode
  distances (`Compute_PerModeSpeed_...`, `GetLeg_PerModeSpeed_...`); with per-mode factors that
  premise no longer holds. They were re-pointed by setting *equal* detour factors so they still
  isolate the per-mode *speed* effect — the guarantee was preserved, not relaxed. The adjusted-
  distance assertion in `Compute_MatchesExpected...` was re-expressed as `haversine × factor`
  (renamed to say what it now proves). No assertion was weakened.
- **A4 — Scope discipline on the manual-leg distance.** `TripViewModel.SetManualLegTimeAsync`
  still records raw haversine distance for a *user-typed* leg time. That is correct and in
  scope: the detour factor belongs to the *estimate* path; a manual leg's duration is supplied
  by the user, so its incidental distance is not an estimate. Flagged in the 1.2 review as LOW/
  observational; intentionally left unchanged (changing it would be out-of-scope gold-plating).
