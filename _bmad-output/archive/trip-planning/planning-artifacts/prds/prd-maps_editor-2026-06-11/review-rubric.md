# PRD Quality Review — Trip Planning for Collections (LucidCartographer)

## Overall verdict
This is a strong, build-ready chain-top PRD: it has a real thesis ("a lens over the collection you already have, not a new thing to learn"), the **Fidelity** + **provider-contract** abstraction is genuine design work that defuses the one decision that could have blocked the build, and almost every FR carries testable consequences an engineer can verify. What's at risk is concentrated and known: the single biggest product decision — which Measured provider ships — is deferred (honestly, behind the Mock default), and one named user journey (UJ-3's flight-plus-ground trip) is only partially served by the v1 single-mode-per-Trip scope. Neither is a defect of the PRD; both are surfaced as Open Questions with `[NOTE FOR PM]` flags. The document is decision-ready as written.

## Decision-readiness — strong
A decision-maker can act on this. The hardest call — "do we need real road routing before we can ship?" — is met head-on rather than smoothed over: §6.2 and OQ1 state plainly that **"Which Measured provider ships as the recommended non-mock default … deferred"** and the `[NOTE FOR PM: this is the open 'real travel time' decision — the Mock keeps v1 unblocked while it's pending.]` callout sits at exactly the right tension. The Open Questions are genuinely open (OQ2's per-Leg mode override, OQ4's "is a badged Placeholder enough … or should the timeline simply show '—'") rather than rhetorical. Trade-offs name what was given up: the scrape alternative is rejected in addendum §C with three concrete reasons (ToS, fragility, cost/latency), not hand-waved. The counter-metrics (SM-C1, SM-C2) show the PRD is willing to name where its own success metrics could be over-optimized — the antidote to the "everything balances" red flag.

### Findings
- **low** OQ2 / UJ-3 tension under-flagged in the journey itself (§2.3, OQ2) — UJ-3 ("Any/Air mode for the flight leg," then ground stops) is the forcing function for per-Leg mode override, but the deferral lives in §6.2/OQ2 while the UJ reads as fully supported. The `[NOTE FOR PM: directly relevant to the Any/Air + ground combination in UJ-3; revisit early.]` is present but in §6.2, not adjacent to UJ-3. *Fix:* add a one-line edge-case note in UJ-3 that mixed-mode is served in v1 only via the Any/Air Manual Travel Time slice.

## Substance over theater — strong
Content is earned, not furniture. The three personas (Yurik, Mara, Priya) each drive distinct, load-bearing requirements: Yurik → toggle/reorder/Unplaceable (FR-1–4), Mara → TSP-Sort + MCP soft-constraint ordering (FR-15/16), Priya → mobile feasibility + overrun flag (FR-13). None is decorative; three is under the four-persona ceiling. The Fidelity concept ("a number is never mistaken for more than it is," §3) is real innovation that propagates consistently into badging, fallback (FR-10), map line style (FR-6), and metrics (SM-3). The Vision is product-specific — "converts LucidCartographer from a *place keeper* into a *trip thinker*" could not be swapped into an arbitrary PRD. NFRs (§10) cite concrete project anchors (`Viewport.IsMobile` → `Mobile*Screen`, `UiStrings`, `StateChanged`) rather than "must be scalable/secure."

## Strategic coherence — strong
There is a clear thesis and the features follow from it. The bet — trip planning as a *view over an existing entity* ("One Collection ⇔ one Trip," §3; "not a new thing to learn," §1) — drives the most consequential scoping choices: no Trip entity, no day/date concept (overnight = large Dwell Time), Trip View as a display toggle. Success Metrics validate the thesis rather than measuring raw activity: SM-1 measures *adoption of the lens*, SM-2 measures whether assisted ordering is *kept* (engagement quality, not just clicks), and counter-metric SM-C1 explicitly guards the thesis ("Don't trade away the plain Collection"). MVP scope is coherently an *experience/capability* kind, and the scope logic matches. This does not read as a backlog with headings.

## Done-ness clarity — strong
This is the dimension downstream story creation leans on, and it holds up under an unforgiving read. Nearly every FR has a "Consequences (testable)" block with verifiable conditions: FR-5 gives exact counts ("N placeable Stops in a Roundtrip produce N Legs … a Start≠Finish Trip produces N−1 Legs"); FR-15 states a checkable invariant ("total Travel Time ≤ the pre-sort order for the same Stops and Mode"); FR-2 specifies "contiguous (no gaps) and unique." Performance is bounded, not adjectival: SM-5 gives "p95 ≤ 3 s with a warm matrix" for N≤30. Graceful-degradation language (FR-10) is pinned to observable outcomes ("every affected Leg still shows a Travel Time badged Estimated; no Leg is left blank"), avoiding the "handles X gracefully" trap by defining what graceful means.

### Findings
- **medium** FR-7 "highlights" / "pans" lack an observable bound (§4.2, FR-7) — "Selecting a list Stop pans/highlights its marker" is the one place a tester can't tell what passing looks like (no statement of what highlight is, or that selection is single-valued). *Fix:* state the testable consequence (e.g. exactly one marker is in the highlighted state at a time; map centers the selected marker into view).
- **low** FR-13 time-budget input location undefined (§4.4, FR-13; OQ9) — the overrun flag is testable, but "a user-set time budget" has no FR describing where it's set; OQ9 acknowledges this. Harmless for the flag's own AC, but a story author will hit the gap. *Fix:* note in FR-13 that the budget input surface is pending (OQ9) so the flag AC isn't blocked on it.

## Scope honesty — adequate
Omissions are explicit and do real work. §5 Non-Goals carries `[NON-GOAL for MVP]` tags on the silently-assumable ones (navigation app, multi-day calendar) and §6.2 lists deferrals with rationale. `[ASSUMPTION]` tags sit on genuine inferences (toggle persistence granularity, seed order, Dwell-on-membership) and every one round-trips into the §9 Assumptions Index. De-scoping is proposed openly, never done silently — the Mock-default-keeps-v1-unblocked logic is stated three times (§1, §6.1, §6.2). Open-items density is the one thing to watch for a green-light PRD: 9 Open Questions + 10 indexed assumptions + 3 `[NOTE FOR PM]` callouts is a high count. For a launch-grade build it is acceptable because the load-bearing ones (provider default, mode override) are isolated behind a working default, and most assumptions are low-stakes UX/seed choices — but it is at the upper edge of what "ready to build" tolerates.

### Findings
- **medium** Open-items density high for a launch-grade PRD (§8, §9) — 9 OQs and 10 assumptions is a lot to leave open at green-light. Most are low-stakes, but they are presented as a flat list with no priority, so a reader can't quickly see that only OQ1 and OQ2 are build-shaping. *Fix:* tag OQs as blocking vs. non-blocking (or order them so the two build-shaping ones lead), making the honesty of "the rest are cosmetic" legible.

## Downstream usability — strong
As an explicit chain-top feeding `bmad-ux`, `bmad-create-architecture`, and `bmad-create-epics-and-stories` (§0), this matters most, and it is well-served. The Glossary (§3) is thorough and the domain nouns (Stop, Leg, Fidelity, Travel-Time Provider, Stop Order) are used verbatim across FRs, UJs, SMs, and NFRs. Each FR cross-references via Glossary terms and section numbers ("§4.2", "FR-15") rather than "see above," so sections survive extraction. Every UJ has a named protagonist carrying context inline. SMs name which FRs they validate ("Validates FR-15, FR-16"). The companion addendum cleanly carries the technical-how (data model, algorithm, provider comparison) out of the capability narrative, giving architecture a clean source without polluting the PRD.

### Findings
- **low** FR numbering is non-contiguous in document order (§4.1) — FR-17 appears inside §4.1 between FR-4 and §4.2's FR-5, because IDs are globally numbered but FR-17 was added to the first feature later. IDs are unique and all resolve, but a reader scanning top-to-bottom hits 1,2,3,4,17,5,6… *Fix:* either renumber so document order is monotonic, or add a one-line note that FR IDs are stable/global and not positional.

## Shape fit — strong
The shape matches the product. This is a consumer-facing capability with meaningful UX on a self-hosted app, so the three named-protagonist UJs are load-bearing and correctly present, not overhead. It is also brownfield, and the existing-code references are precise and used as constraints: `PoiEnrichmentBackgroundService` (FR-11 background pattern), `leafletInterop.js`/`LeafletMap.razor`/`LeafletMapService.cs` (map interop, §12), `Viewport.IsMobile`→`Mobile*Screen` (NFR), the `/mcp` auth guard (FR-16), EF Core/`IDbContextFactory` conventions (addendum §A). New trip semantics are clearly distinguished from the unchanged existing Collection/POI entities ("**POI** — … Unchanged by this PRD," §3). The PRD is neither over-formalized (no UJ padding) nor under-formalized (the consumer surface has its journeys). The non-functional rigor is calibrated to launch-grade stakes without inflating.

- **Assumptions Index roundtrip:** complete. All 10 inline `[ASSUMPTION]` tags appear in §9, and all §9 entries trace back to an inline tag and FR.
- **ID continuity:** FR IDs are unique and every cross-reference resolves (FR-1…FR-17, SM-1…SM-5/SM-C1–C2, UJ-1…UJ-3, OQ1–9). The only wrinkle is positional: FR-17 sits inside §4.1 ahead of FR-5 (see Downstream finding) — a numbering-order quirk, not a broken ref.
- **UJ protagonists:** each UJ (Yurik, Mara, Priya) names a protagonist and carries entry-state/context inline; no floating UJs.
- **Cross-refs to addendum:** §4.6, §11, §12 point to specific addendum sections (§B, §C, §G); all targets exist.
- **Required sections:** Vision, Target User/JTBD, UJs, Glossary, Features/FRs, Non-Goals, MVP Scope, Success Metrics + counter-metrics, Open Questions, Assumptions Index, NFRs, Constraints, Integration/Deployment — all present for a launch-grade chain-top PRD.
